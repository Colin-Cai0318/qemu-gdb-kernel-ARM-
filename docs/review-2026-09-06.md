# Linux 6.12 实验台复查（2026-09-06）

## 本次修复

| 问题 | 影响 | 修复和验收 |
|---|---|---|
| 仅 A02 Makefile 准备外部模块链接依赖 | 新内核完成 Image 构建后，A01 可能缺 `scripts/module.lds`；customized 未指定 ARM64 工具链 | 主构建添加 `modules_prepare`；统一 A01/A02/customized 参数，实编 AArch64 模块 |
| A02 批处理中不检查停止标志 | 卸载请求后仍处理已取出的全部事件，停止语义不清晰 | 每事件检查 stop，带停止条件的超时等待；积压场景取消剩余事件 |
| `sleep_ms` 可并发修改且只在睡眠处截断 | 展示值可能与实际值不一致，读取缺少同步 | 参数初始化时截断并设为运行期只读，验证 5000 显示为 1000 |
| proc 节点先发布再初始化 worker | 读者可能访问尚未稳定的 worker 指针 | 线程创建成功后才发布 proc；发布失败同步停止线程 |
| 测试仅 grep 线程名，且接受超时退出码 | 缺关键 trace 或打印 PASS 后卡死仍可能被判通过 | 按 PID 检查 waking/wakeup/switch/睡眠顺序；所有超时失败；检查内核诊断、三轮卸载顺序与计数 |
| 自动测试结束删除全部日志 | 失败复盘缺少原始证据 | `artifacts/A02/run.*` 保存串口、构建状态和 SHA-256，临时 rootfs 单独清理 |
| GDB Stub 监听所有接口 | 调试端口向 VM 网络开放 | 默认 loopback；实测 GDB 命中 `start_kernel` |

## 实际验证

- ARM64 Linux 6.12.0，GCC 11.4.0，沿用已构建的 debug Image/vmlinux 和可用 BusyBox rootfs。
- A01、A02、customized 均可用 ARM64 工具链编译；A02 checkpatch 为 0 errors / warnings / checks。
- 真实 QEMU 回归覆盖：正常 3 事件、目标 PID 调度事件链、积压取消、5 秒内停止、空闲卸载、参数上限和 proc/任务清理。
- 正常轮次处理 3 个事件；积压轮次共写入 33 个事件，修复版处理 2 个后停止；空闲轮次为 0。
- 旧模块对照实验中，停止后仍快速处理完 33 个事件。Linux 6.12 `kthread_stop()` 设置
  `TIF_NOTIFY_SIGNAL`，会使旧版可中断睡眠提前返回，因此本次并未观察到最初预测的约 30 秒延迟。
  验收使用实际计数和顺序，不能把“卸载必须等满 sleep_ms”当作正确结论。
- 14 项 Python 测试覆盖不完整证据、顺序/计数/PID 错误、内核异常、版本不符、QEMU 非零退出和输出 PASS 后超时；CI 运行相同测试。
- 真实 GDB 在 loopback Stub 命中 `start_kernel()`，回溯至 ARM64 `__primary_switched`。

## 使用和边界

```bash
./scripts/check.sh
python3 -m unittest discover -s tests -v
make -C labs/A02
KDIR="$PWD/kernel/sourceCode" ROOTFS_STAGING="$PWD/busybox/root" ./labs/A02/validate-qemu.sh
```

本次没有重编整个内核，也没有做 KASAN/lockdep、长期并发压力或所有 Linux 6.12.y
版本兼容性验证。内核 release 一致只是前置条件，构建同源性仍需结合指纹与启动日志。
`handled` 是已开始处理事件的计数；卸载允许取消剩余事件，不能用它推断全部写入都已完成。
已有学习报告及其完成状态没有因维护者回归通过而改变。
